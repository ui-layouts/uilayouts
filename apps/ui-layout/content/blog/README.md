# Editorial workflow

Write a standalone MDX article with no H1 (the route owns the title). Add its entry in `lib/blog.ts` and explicit lazy import in `lib/blog-content.ts`. Use the live preview keys from existing component docs, or a validated block preview path. Each article should teach a distinct technique, give a focused example, and include accessibility and testing advice. Link to the actual source and avoid claims about accessibility, performance or search rankings that have not been verified. Before release, run the app build and check each live preview and canonical route. Update the post date only when appropriate. The index, related links and sitemap derive from the metadata.

Every post must have a cover in `components/website/blog/blog-cover.tsx`. Prefer existing library artwork and block images; use clearly illustrative diagrams where an actual screenshot is not available. Do not use unrelated third-party UI screenshots. Live examples should use the exact preview keys in the component documentation. The blog uses the shared website Container, not a separate page width.

Coverage policy: every public component route in DocsNavigationCategories must have at least one dedicated tutorial. Run `node scripts/check-blog-coverage.mjs` from the app directory to check the catalog, article loaders, MDX files and cover entries. Titles should express a concrete task or question a developer might search for, rather than repeat a registry name. Avoid claiming measured keyword demand or guaranteed rankings.
